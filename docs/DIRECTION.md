# Payo Kapot — 動態版前／後台方向

現有 `index.html` 是**單機原型**（本機儲存）。動態版目標：多人可同時用、資料進伺服器、分前台使用與後台管理。

---

## 1. 兩套入口，一種資料

| | 前台（使用端） | 後台（管理端） |
|---|---|---|
| 給誰 | 級長、工作人員、一般族人 | 頭目／幹部、名冊管理員、系統管理者 |
| 目的 | 查人力、回報狀態、接任務 | 維護名冊、階級、活動、權限 |
| 語氣 | 簡單、手機優先 | 完整、桌機也可 |

建議網址概念：

- 前台：`/app`（或部落自訂網域）
- 後台：`/admin`

---

## 2. 角色權限（建議四層）

1. **訪客／族人**：看公開看板（各階人數）、看自己的資料、更新「可否動員」
2. **級長（kapot 幹部）**：看本級完整名冊、標記本級出勤、發本級通知
3. **部落管理員**：全名冊 CRUD、階級設定、活動／工作編排、匯出
4. **系統管理者**：多部落（若需要）、帳號權限、備份與稽核

先做「部落管理員 + 一般族人」兩層就夠上線；級長權限第二期再加。

---

## 3. 前台：使用者每天會做的事

### A. 人力看板（首頁）
- 本部落各階級人數、可動員人數
- 進行中的活動（例如：豐年祭準備、會所整修）
- 我被分到的工作（若已登入）

### B. 我的資料
- 中文名、族語名、階級、電話、專長
- 一鍵更新動員狀態：可動員／視情況／長期在外
- （選配）上傳大頭照或聯絡偏好

### C. 本級名冊（登入後・手風琴）
- 預設只露出「華語名＋族語名」（必要時加階級）
- 點開手風琴才依權限顯示更多欄位（見下方「限制公告」）
- 可依階級分組，或同級內再摺疊每一人

### D. 活動報到／回報（第二期）
- 活動當天：到場打勾、請假
- 級長看本級出席率

前台不做複雜設定；設定全部放後台。

## 3.1 前台名冊 UI：手風琴 + 限制公告（個資）

前台適合用手風琴（accordion）：**摺起＝公告層，展開＝授權層**。  
名單可以給需要動員的人看，但電話、備註等個資不要一次攤在畫面上。

### 建議三層揭露

| 層級 | 誰看得到 | 手風琴狀態 | 顯示內容 |
|---|---|---|---|
| **公開／弱公告** | 未登入或僅有連結的人（可選關） | 只見人數，或根本不列姓名 | 各階人數、可動員人數；**不列個人姓名** |
| **名冊公告（預設摺起）** | 已登入族人 | 摺起列 | **華語名字、族語名稱**；（可選）階級徽章 |
| **詳情（展開後）** | 依角色再拆 | 點開才見 | 見下表 |

### 展開後依角色顯示

| 欄位 | 本人 | 同級族人 | 級長 | 管理員 |
|---|---|---|---|---|
| 華語名／族語名 | ✓ | ✓ | ✓ | ✓ |
| 階級 | ✓ | ✓ | ✓ | ✓ |
| 專長（可動員相關） | ✓ | ✓（建議） | ✓ | ✓ |
| 動員狀態 | ✓（可自己改） | △ 可只顯示「可／否」 | ✓ | ✓ |
| 電話／Line | ✓ | ✗ 或需本人同意 | ✓（本級） | ✓ |
| 備註／地址／敏感說明 | ✓ | ✗ | △ 最小化 | ✓ |

原則：**預設最小必要**；聯絡方式不要當公告，當「授權後的工作資訊」。

### 手風琴互動建議

1. **一列一人**：左／上方是 `華語名`，下方或右側小字是 `族語名`；右側用 ▾ 展開。  
2. **一次只開一個**（同層 accordion）：減少螢幕同時曝光多筆電話。  
3. **展開區標題標示「僅授權可見」**，避免誤以為全站公開。  
4. **電話用按鈕**：`顯示電話`／`複製`／`撥打`，不要一展開就明文整排列出（降低肩窺與截圖風險）。  
5. **搜尋**：可搜華語名、族語名、專長；搜尋結果仍先摺起，不因搜尋就爆出電話。  
6. **列印／截圖**：前台不提供「含電話的一鍵列印」；完整名冊只從後台匯出，並留操作紀錄。

### 同意與後台開關（務必有）

後台為每位族人（或全部落預設）提供勾選：

- [ ] 允許同級看到我的專長  
- [ ] 允許級長看到我的電話  
- [ ] 允許出現在前台名冊公告（華語名＋族語名）  

未勾「出現在前台名冊」者：前台不算進可點開的名單（人數統計仍可匿名計入）。

### 為什麼這樣建議

- **華語名＋族語名**剛好是動員時辨識「這個人是誰」的最小組合，適合當摺起列。  
- 手風琴把「認人」和「拿聯絡方式」分開，符合個資最小化。  
- 部落情境常需在會所傳手機看名單：摺起＋一次只開一筆，比表格一次噴全部更合適。

## 4. 後台：管理員要能操作的事

### A. 名冊管理
- 新增／編輯／停用族人（停用優於硬刪，保留歷史）
- 批次匯入 CSV、匯出 Excel／CSV
- 依階級、動員狀態、專長篩選

### B. 階級設定
- 級名、順序（幼→長）、職責說明
- 晉級作業（整批把某級升到下一級）— 豐年祭後最常用
- 級長指派（綁定帳號 ↔ 階級）

### C. 活動與工作（人力真正「被用起來」的地方）
- 建立活動：名稱、日期、地點、需要哪些階級／專長、人數
- 從名冊勾人選人，或依條件自動建議
- 匯出當次工作分配表

### D. 帳號與權限
- 邀請連結／帳號開通
- 角色：族人／級長／管理員
- 操作日誌（誰改了誰的階級、誰匯出了名冊）

### E. 部落基本資料
- 部落名稱、對外簡介
- 是否公開「人數看板」（可只顯示人數、不顯示姓名）

---

## 5. 核心資料模型（動態版最小集）

```
部落 Tribe
  └─ 階級 Grade（順序、級名、職責）
  └─ 族人 Member（姓名、族語名、gradeId、專長、動員狀態、聯絡）
  └─ 使用者 User（登入帳號，可綁 Member）
  └─ 活動 Event
        └─ 任務 Task（需要的人／專長）
        └─ 指派 Assignment（誰負責、是否確認／到場）
```

之後可加：晉級紀錄、通知、留言、檔案附件。

## 6. 建議技術方向（務實、好維護）

與「之後做動態網頁」對齊，建議一條主線，避免過度拆分：

| 層 | 建議 | 理由 |
|---|---|---|
| 前端 | Next.js（或 Nuxt）+ 手機優先 UI | 前台／後台同一專案，路由分開即可 |
| 後端 API | 同框架 Route Handlers，或獨立 FastAPI | 名冊、權限、匯出都走 API |
| 資料庫 | PostgreSQL（Supabase / Neon 亦可） | 關聯清楚：部落–階級–族人–活動 |
| 登入 | 手機 OTP、Google、或魔術連結 Email | 族人不見得要記密碼 |
| 檔案 | 先不做大檔；CSV 匯出入 DB 即可 | 降低前期複雜度 |
| 部署 | Vercel / Cloudflare + 託管 DB | 靜態原型可繼續當展示，動態版另站 |

原型 `index.html` 可保留為：展示頁、或離線備援匯出格式對照。

## 7. 分期（照這個做不會一次做太大）

### 第一期 — 能共用的名冊（上線最小）
- 登入（管理員 + 族人）
- 後台：階級、族人 CRUD、CSV 匯出
- 前台：看板 + 我的動員狀態
- 單一部落

### 第二期 — 用得上人力
- 活動／工作指派
- 級長看本級
- 通知（LINE Notify / 簡訊／Email 擇一）

### 第三期 — 對齊歲時
- 批次晉級
- 歷年名冊快照（某年豐年祭當下的人力）
- 多部落（若 Payo 要服務多個部落）

---

## 8. 前／後台操作情境（驗收用）

1. **管理員**：後台匯入名冊 → 設好六個級名 → 指派級長帳號  
2. **族人**：手機打開前台 → 更新「這個月可否回部落」  
3. **級長**：看本級誰可動員、誰有「架設」專長  
4. **管理員**：建立「會所整修」活動 → 從可動員青年級勾 10 人 → 匯出工作表  
5. **豐年祭後**：後台執行晉級，名冊階級一次更新，看板數字跟著變  

這五步都能跑完，動態版就算「可操作、可使用」。

---

## 9. 與現有靜態版的關係

| 現有靜態版 | 動態版 |
|---|---|
| localStorage | 資料庫 |
| 任何人開同一瀏覽器都能改 | 權限分級 |
| 示範級名可改 | 後台正式維護級名 |
| JSON／CSV 本機檔 | 雲端名冊 + 仍可匯出備份 |

建議：動態版 API 的匯出 JSON 盡量相容現有結構（`tribeName` / `grades` / `members`），方便遷移。
